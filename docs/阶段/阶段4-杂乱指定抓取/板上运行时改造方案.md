## 0. 原则与边界

**运行时回路只在板上。** 一轮真机实验的令牌窗口内任务（预检 → 观察 → 解垫 → 探针 → 规划
（含碰撞裁决）→ 执行 → 跑后真值 → 判分）100% 在板上串成一条进程链。开发机只剩：
发起（一条 ssh）、观察（只读轮询）、归档拉取（NAT 所限、只在 `round-done.json` 之后）、
离线排练 / 回归测试 / 判分复核 / 仿真与训练。

为什么规划也必须上板：开发机不能当 ROS 节点（跨机 DDS 是坏的）⇒ **自碰撞检查在规划侧根本
无法接线**——这是 attempt6 夹爪撞臂（C153A3）的结构性根因。板上规划进程与 `move_group`
同机同图，`/check_state_validity` 才能成为计划的落盘前闸门。

## 1. 目标架构

```
开发机（离线）                      板子（Orin NX，运行时唯一权威）
──────────────                    ─────────────────────────────
launch_round.py ──ssh 发起──▶  stage4_round_board.sh（板上，flock 单例）
watch_round.py ──ssh 轮询──▶      ├─ 0 预检（本地直跑；含 URDF 指纹）
archive_pull   ──rsync 拉──▶      ├─ 1 观察计划（规划后端，板上）
                                  ├─ 2 授权（先起 auth 监听、再请人按 STOP→PLAY）
                                  ├─ 3 观察执行（JTC + burst）
                                  ├─ 4 计算：解垫→探针→规划(urkin|curobo+自碰撞裁决)→R2
                                  ├─ 5 执行（precision_exec，计划 JSON v2 不变）
                                  ├─ 6 判分（score / round_report，本地 JSON）
                                  └─ 7 落 round-done.json（归档由 dev 拉）
```

仿真链现状不变：Gazebo 在开发机，板子经 SSH 反向隧道 + TCP JSON 桥（`sim_bridge` /
`sim_board_agent`）控制仿真臂——**跨机不走 DDS 是这条链已经解决过的问题**，规划后端
上板后仿真路径照旧（板上规划 → 桥上执行）。

## 3. 规划后端抽象（切换设计）

**契约冻结：计划 JSON v2 schema 是唯一对外接口。** 执行端（`precision_exec`）、闸门
（R1/R2 估时读 waypoint duration）、判分（读计划 meta）**零改动**——后端切换是数据级切换。

```
PlannerBackend（协议，scripts/planner_backend.py）
    plan_cycle(scene, actions, q_start, views) -> [计划 JSON v2]
    抛 pp.PlanError / BranchChainError / JointSwingError（异常语义两后端一致）

UrkinBackend   = 现行路径：solve_path DP + 门限（cap 90°）+ validator 注入
CuroboBackend  = cuRobo IKSolver（collision-aware，批查 8 支）
                 + MotionGen（段内轨迹）→ 降采样回 waypoint 序列（duration 重算）
                 + 同一套软限位/腕奇异/缠绕门复检（门代码共享，不重写）
```

三条不变量：
1. **异常同义**：两后端对"不可达 / 越限位 / 碰撞 / 单步超限"抛同一类异常、同文案关键词
   （编排器只认退出码与异常类）。
2. **门限共享**：软限位、腕奇异（`check_wrist`）、缠绕帽、单步帽、高度护栏在
   `precision_plan` 一处实现，cuRobo 后端**复检**同一套门（GPU 解不直接可信）。
3. **可追溯**：manifest 记 `planner_backend` 字段；切换只经 CLI `--planner urkin|curobo`
   （缺省 urkin），正式轮换后端须在轮命令里显式可见。

cuRobo 侧要点：UR5+AG-95 碰撞球配置（Isaac Sim 生成或 cuRobo 官方 UR5 配置改）；机器人
config 的 URDF 必须与驱动/MoveIt/规划**同源**（依赖 C3 收口）；Orin NX 内存预算
（motion gen 初始化 RSS 增量 ≤2 GiB，板机 7.4 GiB）；cuRobo 不上 ROS——它是规划库，
产出仍是计划 JSON，执行照旧 JTC（阶段 4 内不换执行器）。

## 4. 对比实验协议（两后端怎么判优劣、怎么定切换边界）

**数据集（离线，不动臂）**：
- S0 三布局 × 5 目标（15 个规划链，现役正式批次）；
- 历史回归：s8 / s10 / attempt6 三组真机已跑输入（各含已知答案：可解 / 撞臂应拒）；
- 杂乱压力集：E7 的 4 个失败场景 + E9 S4 塔场景（清障链，cuRobo 的目标场景）。

**指标（每后端 × 每链）**：
| 指标 | 通过线（cuRobo vs urkin） |
|---|---|
| 规划成功率 | cuRobo ≥ urkin（同数据集不丢解） |
| 单链规划耗时（Orin NX 实测） | cuRobo ≤ 2 s / 链（urkin 基线 ~3 s/链按 23 s/8 链折算） |
| 计划质量 | 总关节行程、最大单步、段内最低护栏余量三项并报，cuRobo 不劣于 urkin ×1.2 |
| 碰撞判决一致率 | 与 `/check_state_validity`（A1 之后含夹爪）对账 ≥ 100%（cuRobo 放行的必须过 MoveIt） |
| 确定性 | 同输入 5 次，解集合稳定（cuRobo 关随机性或固定 seed） |
| 资源 | RSS 增量 ≤ 2 GiB；不挤占感知进程（同轮共存实测） |

**切换边界（拍板输入）**：实验报告按上表给出建议——预期结论形态是
"S0–S2 留 urkin（已达标、轻依赖）；S3+ 杂乱/堆叠换 cuRobo（碰撞维度 urkin 没有对应物）"，
但以数据为准，不预先结论。
