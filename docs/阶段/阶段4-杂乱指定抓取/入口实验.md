## 2. E2 俯视第二路 + 双相机联合标定

**判据（判据 B，2026-11-07 用户拍板，台账第二百七十二轮）**：覆盖整桌 + 宫格 + 悬停位；
**连续 5 轮**；每轮腕部 + 俯视各一帧、RMS ≤1.5 px、每页垫 ≥4 标记。
**主判据是自洽性** —— 刚性 ChArUco 板路线逐轮自复现 **≤1 mm / 0.2°** + E3a 漂移门；
**两路垫 PnP 降为交叉核对**：平移 **≤2 mm** 不变、角度 **≤1.2°**（= 这条路线自己的复现性）。
旧判据 A（≤2 mm / ≤0.5°）已由用户显式改掉，理由见 §2.1 与契约 §3.1 的判据修订框。

**做法**：
1. 俯视只发 `base_link → topcam_link`（独立 namespace / `camera_name: topcam`）；
   真机 `publish_camera_tf:=false`（腕部手眼 TF 另有独立发布者，不得出现第二个
   `camera_link` 父节点）。
2. 腕部帧 → `stage2_pad.solve_pad` 得 `base←pad`；俯视帧 → 同一 `solve_pad` 传单位外参
   得 `topcam←pad`；联立 `base←topcam = base←pad ∘ (topcam←pad)⁻¹`。
3. `base←topcam_optical` 用**驱动实测** `topcam_link→topcam_color_optical_frame` 链换算，
   不用理想 link→optical。
4. 第 1 轮解出的外参**才**用来重启发布 TF；不拿旧外参反喂。

**工具**：`real.launch.py`（topcam 参数 / 守卫 / 节点 / TF）、
`precision_capture.py --camera topcam --burst`、`stage2_pad.py --cam-identity`、
`topcam_marker_calib.py --out/--tf-json`、新 `stage4_joint_calib.py`。

**5 轮位姿**：从 `SURVEY_TOOL0["stage2high"]` (0.452, −0.200, 0.547) 出发，
用 `stage3_survey_tool0` 在 ±30–50 mm 内取 5 个横向偏置，保证垫始终在腕部视场内。

**结果 · set-1（2026-11-07，未通过）**：轮 01 导出外参（该轮两路差是代数恒等式，不算证据）；

- 红因：俯视看垫时页 B 长期只有 4–6/10 个标记（臂挡 + 46° 斜视），逐帧 PnP 散布

### 7.3 用户提的修正办法：夹爪夹距当已知长度

思路（2026-11-07 用户原话的意思）：**俯视拍到「夹爪夹着方块」时，用机械上确定的夹爪夹距
和俯视量出的距离对比，把比例/系统偏差修出来**，再用它修正后续测量的位置差。

- 已知量：AG-95 的开合是寄存器给定（0–1000 千分 → mm），两指外侧面间距由机械结构确定，
  是这套系统里**唯一不依赖任何相机**的长度基准。
- 量法：同一帧里取两指外侧面（彩色边缘 + 深度的平面/高度），量间距，与机械值比。
- **精度预算（先算再干）**：俯视在台面上约 **0.64 px/mm**（1280 px / ~2 m 视场）。
  26 mm 开口的 2% = 0.52 mm ≈ **0.33 px ⇒ 单帧不可辨**；100 mm 开口的 2% = 2 mm ≈
  1.3 px ⇒ 单帧可辨、20 帧融合有余量。**所以先用大开口验证，再往小开口推**；
  小开口上只能验证「有没有大偏差」，不能验 1%。
- **前提必须先验**：两指细、金属反光、大概率被所夹方块挡。第一件事是收一帧「夹爪夹着块、
  俯视可见」的图，确认两指在彩色/深度里**能不能稳定分割**。
  **2026-11-08 B1 已做（部分）**：全开（1000 千分）+ 无遮挡的低位帧证明两指**可稳定分割**，
  并顺带测出 **AG-95 开合轴 = `tool0` 的 x 轴**；**夹着块**的那一帧仍未拍（列在队列，
  等第一次真抓取时顺带取，不单独上臂）。分不出就换已知长度：
  方块本身有已知规格（外接边长可当尺度），或 ChArUco 板（已知边长）—— **不许把不可测
  当成可测**。
- **它能修什么**：比例/深度系统偏差（俯视深度读远 ~1.9%、y 向 20–45 mm 偏差的量级）。
  **它修不了倾角地板** —— 那是腕部链条的姿态误差，只能靠 E2 判据 B 的边界兜住，
  或回头做多姿态手眼（判据 A 那条路）。
- **怎么算有效**：修正后在 E4b 对中判据（≤2 mm / ≤2°）内即算有效；若修正前后无差别，
  就记「地板内、无增益」，不硬上。
- 需要一次真机（夹住方块、静止拍俯视），属运动 ⇒ 需当次 STOP→PLAY 授权。

**前提帧 B1 已拍（2026-11-08，✅ 可分；空夹爪、大开口、无遮挡）**

- **几何先算清**：悬停高度（tool0 z=547 mm）俯视**完全看不到夹爪** —— 整个夹爪的投影都在
  画面上沿之外（tool0 落在 v≈−300 px），所以「抓完拍一帧验证」这类设计本来就不可行。
  tool0 降到 **z=360 mm** 时指尖投影到 v≈131 px、进画幅；再降到 240 mm，肘离台面只剩
  35.8 mm（护栏 20 mm）⇒ 取 **360 mm**（肘余量 155.8 mm）。
- **实拍**：`runs/2026-11-08-stage4-entry/e2/set4/b1/topcam/`，20 帧，tool0=(472,−250,360) mm，
  到位误差 0.00°、窗口内关节峰峰 0.005°。**没有写任何夹爪寄存器**，开口沿用上次遗留状态
  （所以这一步不需要夹爪授权）。
- **结论：两指可稳定分割。** 彩色阈值 V<110 把夹爪整体吃住、两指之间保持空白（空隙约
  40–50 px，背景不被误选）；深度窗口内 98.4% 像素有效，两指可见实体的 base 系中心距
  **79 mm**，跨 4 帧一致到 1 mm。
- **附带测出一条一直缺的事实**：AG-95 的**开合轴是 tool0 的 x 轴**。`precision_plan.py` 里
  原先写着「AG-95 的手指轴相对 tool0 的方向没有文档也没实测过」。用 FK 把 x±35 / y±35
  投影回帧上：橙色 x±35 正好落在两只指头上、绿色 y±35 落在指间空隙（等轴几乎平行于
  视线方向）。⇒ 以后要用抓取平面内角时，开合方向 = `Rz(ψ)·[1,0,0]`。
- **还差一步**：本帧是**空夹爪 + 大开口**（最有利几何）。比例修正本身要「夹着块」的帧，
  但**必要前提（可分割）已经成立**，那张帧可以等第一次真抓取时顺带拍，不必单独上臂。

## 8. E5 实例分割 + 指定解析（仿真帧，2026-11-08）

**判据**（契约 §3，逐字）：S0–S2 指定 ID ≥90%（S2 单独报）；中心 / 顶高 ≤2 mm、
yaw ≤5°；解析 100% 可判、0 误配。

### 8.1 数据与口径

- **帧**：每批 **5 个布局**（`index` 0–4），共 15 帧，全部是 **Gazebo 仿真帧**
  （`meta.json` 的 D 全 0、主点恰 (640,360)、时钟 ~100 s）：
  - `index=0`：`notes/ur5-vision-grasp/runs/2026-11-07-stage4-e6/frames-s{0,1,2}/topcam-home/`
  - `index=1..4`：`notes/ur5-vision-grasp/runs/2026-11-08-stage4-e5/frames-s{0,1,2}-{1..4}/topcam-home/`
  - 采帧链：`gen_scene.py`（固定种子）→ `sim.launch.py headless:=true scene:=S0:1`
    → `scripts/sim_capture_frame.py --camera topcam --truth <scene_truth.json>`。
    **WSL 上必须 `export GZ_IP=127.0.0.1`**，否则 gz 话题能列出但**一条数据都收不到**。
- **指定 ID 正确率** = 解析器 top-1 实例（经真值↔实例配对映射后）等于命令目标的命令数 /
  全部命令，**含** ambiguous 时仍返回的那一块。**自主 top-1** 只算 `status=ok` 的。
  **误配** = `status=ok` 却选错，必须 0。
- **命令集不是手写的**：对每个真值块生成所有合法说法（`at` / 方位 / 关系 / 限定词），
  拿**真值块表**跑一遍解析器，只保留**在真值上唯一指向该块**的那些；不唯一的**计数**，
  不静默丢（15 帧合计跳过 **869** 条：S0 204 / S1 311 / S2 354）。
- **另加独立复核**（防评估器同源自证）：评估器**另写一份**唯一性判据，只用真值坐标数
  命中，不复用 `stage4_specify`；两边不一致就判评估器自身可疑。1352 条命令**零分歧**。
- **合并口径**：契约要的是「每批」。多帧合并**合并计数**（总对/总命令），
  不取比率的算术平均 —— 各帧命令数不同，平均会系统性高估；测试里有一条专门钉这个。

### 8.3 两个必须记住的坑

1. **仿真与真机的色相表不是一张**。仿真帧落在真机色相表上会把
   orange→yellow、yellow→yellowgreen 系统性错移一格。已在 `block_classes.py` 里
   分列 `MEASURED_HUE_DEG`（真机暖白光）与 `SIM_HUE_DEG`（gz 渲染，17 块实测），
   `nearest_class_by_hue` 加 `table=` 参数；**仿真帧必须传 sim 表**，混用会静默错一格。
   自检里有一条**专门钉这个陷阱**：sim 的 orange（38.5°）在真机表下必须被判成 yellow。
2. **base 系方位约定由本阶段定义**：`+x = 前`、`+y = 左`（ROS 惯例，机器人视角），
   方位在**同色实例之间**比。契约未钉这一条，是本阶段落的；已在
   `stage4_specify.py` 模块 docstring 里写明是**唯一定义处**。
